# v1.34 Workshop Checker Inventory

**Phase:** 238 - Workshop Checker Path Inventory and Public Contract
**Date:** 2026-06-01
**Scope:** TypeScript, Python, Rust, and Zig Workshop Validate source, submit/save, account save, and entry paths.

## Executive Summary

Workshop validation is close to the provider model, but not yet contract-unified. The main parity gaps are:

- Workshop Validate source routes TypeScript, Rust, and Zig through runtime-service when configured, but Python still uses local Workshop validation.
- Workshop submit/save is stricter than Validate source because it requires runtime-service provider validation for all four languages before building a Workshop Revision.
- Account save through Go validates Python/Rust/Zig through runtime-service, but TypeScript is still locally validated in Go without TypeScript provider proof.
- Entry gates consume saved Revision metadata rather than source. Persistence ladder/counting paths require provider proof for all four languages, while selected Go exhibition eligibility is looser for TypeScript and non-counted exhibitions.
- Current diagnostics are still `StrategyRevisionValidationReport`-centric. They do not expose a shared checker status, diagnostic category, actionability, provider id, artifact/provenance state, runtime-service availability, toolchain availability, or cache identity.
- Current default/public paths mostly avoid raw diagnostics, but runtime-service success metadata can contain artifact bytes internally, and some error messages include runtime-service failure code/message. The new checker contract must normalize before public/default output.

## Path Inventory

### Workshop Validate Source

**Frontend path**

- `apps/web/app/workshop/workshop-client.tsx`
  - `validateSource` posts `{ source, sourceFormat }` to `/api/workshop/validate`.
  - Validation freshness is tied to `validationSource === source` and `validationSourceFormat === sourceFormat`.
  - Dirty edits auto-trigger validation after 500 ms.
  - Manual button is labeled `Validate source`.
- `apps/web/app/workshop/workshop-client-state.ts`
  - Current states are `not-checked`, `checking`, `valid`, `invalid`.
  - Issue heading is `SEVERITY / CODE`.
  - Guidance uses `constraint`, `message`, `remediation`, and `reference`.

**App/API route**

- `apps/web/app/api/workshop/validate/route.ts`
  - Accepts `sourceFormat` values `typescript`, `python`, `rust`, `zig`.
  - Calls runtime-service `/validate-strategy` for TypeScript, Rust, and Zig when `COWARDS_RUNTIME_SERVICE_URL` is configured.
  - Returns a fake invalid `TRANSPILE_FAILED` report when runtime-service URL is missing for TypeScript, Rust, or Zig.
  - Falls back to `workshopServer.validateSource` for Python.
  - Returns only `{ validation }`, losing runtime-service HTTP/error semantics and provider metadata.

**Provider boundary**

- TypeScript/Rust/Zig Validate source can cross to runtime-service.
- Python Validate source does not currently cross the runtime-service boundary through this route.
- Local Rust/Zig fallback in `packages/persistence/src/workshop.ts` is only an entrypoint/string heuristic and not provider-grade compile/import/artifact validation.

### Workshop Submit/Save

**Frontend path**

- `apps/web/app/workshop/workshop-client.tsx`
  - `submitRevision` posts `{ source, sourceFormat, label, notes }` to `/api/workshop/revisions`.
  - Save-to-account uses `/api/account/revisions/save`.
  - The client gates both submit and account save on the current valid Workshop validation.

**App/API route**

- `apps/web/app/api/workshop/revisions/route.ts`
  - Accepts all four production source formats.
  - Calls runtime-service `/validate-strategy` for TypeScript, Python, Rust, and Zig before `workshopServer.submitSource`.
  - On invalid provider validation, returns `{ ok: false, validation }` with status 422.
  - On missing runtime-service URL, returns status 503 with a plain `{ error }`.
- `apps/web/app/workshop/server.ts`
  - `submitSource` requires `runtimeServiceValidated === true` for all four production languages.

**Persistence/build path**

- `packages/persistence/src/workshop.ts`
  - `buildWorkshopRevision` requires runtime-service-backed metadata for TypeScript, Python, Rust, and Zig.
  - TypeScript requires `sourceArtifact` format `transpiled-javascript` plus provider validation proof for `strategy-language-provider-js-ts`.
  - Python requires `sourceArtifact` format `python-source-bundle` plus provider validation proof for `strategy-language-provider-python`.
  - Rust/Zig require immutable `compiledArtifact` metadata and provider proof.
  - Public Workshop revision metadata strips artifact byte payloads such as `bytesBase64`.

### Account Save

**App/API route**

- `apps/web/app/api/account/revisions/save/route.ts`
  - Delegates to `saveAccountRevisionFromRequest`.
- `apps/web/lib/account-revision-write-boundary.ts`
  - Validates only that `sourceFormat` is one of TypeScript/Python/Rust/Zig.
  - Delegates account revision creation to the selected Go backend client.

**Go backend path**

- `apps/go-backend/live_backend.go`
  - `createStrategyRevision` accepts TypeScript, Python, Rust, and Zig.
  - TypeScript uses local Go `validateSourceMetadata`, which is a source-size, substring, and forbidden-marker check. It does not call runtime-service and does not require TypeScript provider proof.
  - Python calls `runtime.validateStrategy` and stores runtime-service validation/runtime/engine/metadata on success.
  - Rust and Zig call `runtime.validateStrategy` and expect runtime-service compile/artifact metadata.
  - Invalid runtime-service validation can be saved as an invalid revision with default runtime metadata and minimal tags.
  - Runtime-service transport/contract/source mismatch failures become broad `RUNTIME_SERVICE_UNAVAILABLE` API errors with runtime-service failure code/message included.
- `apps/go-backend/runtime_service_client.go`
  - `validateStrategy` currently accepts Python/Rust/Zig and rejects TypeScript client-side, even though runtime-service supports TypeScript.
  - It verifies source hash and byte identity on successful validation responses.
  - It caps response bytes and classifies transport/read/malformed/contract/source mismatch failures internally.

### Competition and Entry Paths

**Exhibition entry**

- `apps/web/app/exhibitions/new/exhibition-client.tsx`
  - Uses saved revision summaries.
  - Filters valid revisions and counted eligibility client-side.
- Selected Go exhibition path in `apps/go-backend/live_backend.go`
  - `createExhibition` -> `createExhibitionMatchSet` -> `loadOwnedEntrants`.
  - Requires owned revision, `validation.valid`, and runtime eligibility.
  - Counted TypeScript eligibility in Go is looser than the persistence path because it does not require TypeScript provider proof.
  - Non-counted exhibitions can allow Python/Rust/Zig by runtime metadata without provider proof.
- TypeScript persistence competition path in `packages/persistence/src/competition.ts`
  - `runtimeAllowsCountedPlay` requires provider-validated artifact/revision provenance for TypeScript, Python, Rust, and Zig.

**Trial ladder entry**

- `apps/web/app/api/ladder/seasons/[seasonId]/entries/route.ts`
  - Accepts `{ revisionId }` and delegates to `competitiveServer.enterTrialLadderSeason`.
- `apps/web/app/competitive/server.ts`
  - Calls persistence `enterTrialLadderSeason`.
- `packages/persistence/src/ladder.ts`
  - `assertLadderEligibleRuntime` requires provider proof for TypeScript, Python, Rust, and Zig.
  - Entry consumes saved Revision metadata; it does not validate source live.

### Runtime-Service and Provider Validators

- `apps/runtime-service/src/server.ts`
  - `/validate-strategy` accepts TypeScript, Python, Rust, and Zig.
  - Dispatches to provider validators.
  - Invalid source returns status 422 with only `validation`.
  - Successful validation returns provider metadata, runtime metadata, validation, engine compatibility, provider-proof metadata, source hash, and source bytes.
- `packages/runtime-js/src/source-artifact.ts`
  - TypeScript emits `sourceArtifact` format `transpiled-javascript` with `sandboxClaim: provenance-only`.
- `packages/runtime-python/src/validation.ts`
  - Python emits normalized `sourceArtifact` format `python-source-bundle` with `sandboxClaim: provenance-only`.
  - Policy/import/package/syntax failures currently map mostly to `IMPORT_NOT_ALLOWED`, `FORBIDDEN_PATTERN`, or `TRANSPILE_FAILED`.
- `packages/runtime-wasm-wasi/src/validation.ts`
  - Rust emits `compiledArtifact` for `wasm32-wasip1`, `preview1`, `stdin-stdout-json`.
  - Zig emits `compiledArtifact` for `wasm32-wasi`, `preview1`, `stdin-stdout-json`.
  - Toolchain unavailable and compile failure are currently both `TRANSPILE_FAILED`.
  - Forbidden imports are currently `FORBIDDEN_PATTERN`.

### Runtime Broker Boundary

- Current Workshop checker and submit/save validation paths call runtime-service `/validate-strategy` directly.
- The Runtime Broker is represented in provider metadata, selection policy, and runtime-service/provider ownership language, but there is no separate concrete broker process or hop exposed in the current Workshop checker route.
- The checker contract should therefore describe the hostile-code boundary as runtime-service / Runtime Broker / provider, while inventory artifacts should map the concrete current path as app/API or Go -> runtime-service -> provider validator/compiler.
- Phase 239 should avoid introducing a web/API/Go-hosted broker behavior; any future broker process remains an implementation detail behind the runtime-service/provider boundary.

## Per-Language Findings

### TypeScript

- Runtime-service supports TypeScript provider validation and source artifact provenance.
- Workshop Validate source uses runtime-service when configured.
- Workshop submit/save requires TypeScript runtime-service provider validation.
- Go account save and selected Go exhibition eligibility do not yet require TypeScript provider proof.
- Persistence competition and ladder paths do require TypeScript provider proof.
- TypeScript remains the practical checker baseline for user-facing Workshop flow, but backend ownership paths are not semantically identical.

### Python

- Runtime-service supports Python provider validation and source artifact provenance.
- Workshop Validate source currently uses local validation instead of runtime-service.
- Workshop submit/save and Go account save use runtime-service provider validation.
- Entry paths require saved valid revisions and provider proof for counted ladder/persistence competition paths.
- Python diagnostic categories need separation for policy/capability, forbidden import, package/dependency, syntax/build, provenance, runtime-service unavailable, timeout/limit, and invalid output/schema.

### Rust

- Runtime-service supports Rust compile/artifact validation and provider proof.
- Workshop Validate source uses runtime-service when configured, but missing runtime-service URL becomes generic `TRANSPILE_FAILED`.
- Workshop submit/save and Go account save use runtime-service provider validation.
- Entry paths consume saved runtime/artifact proof; persistence gates require provider proof.
- Rust diagnostic categories need separation for compile, artifact/provenance, forbidden WASI/import, runtime-service, toolchain unavailable, timeout/limit, and invalid output/schema.

### Zig

- Runtime-service supports Zig compile/artifact validation and provider proof.
- Workshop Validate source uses runtime-service when configured, but missing runtime-service URL becomes generic `TRANSPILE_FAILED`.
- Workshop submit/save and Go account save use runtime-service provider validation.
- Entry paths consume saved runtime/artifact proof; persistence gates require provider proof.
- Zig diagnostic categories need separation for compile, artifact/provenance, forbidden WASI/import, no-std/helper misuse, runtime-service, toolchain unavailable, timeout/limit, and invalid output/schema.

## Boundary and Privacy Notes

- No inventory evidence showed Strategy execution moving into web/API/Go.
- Web/API and Go currently treat runtime-service/provider validation as external data, though the checker contract should require schema validation before returning provider output.
- Runtime-service success metadata may include artifact byte payloads for internal proof, but default/public checker output must not expose bytes or `bytesBase64`.
- Runtime-service and Go errors should become normalized public categories rather than exposing raw failure code/message strings by default.
- TinyGo is absent from Workshop production source-format lists and should remain absent.

## Phase 239 Inputs

Phase 239 should fix the `fix now` gaps from the parity matrix by implementing a unified checker contract at `/api/workshop/validate`, routing Python Validate source through provider-grade validation, normalizing unavailable/toolchain states, and preserving submit/save/entry ownership boundaries.
