# v1.35 and v1.36 Milestone Prompt Drafts

Prepared: 2026-06-14

## v1.35 Prompt

We're starting Coward's Game v1.35.

Please create a new GSD milestone with no workstream: "Runtime, Account Ownership, Sandbox, and Package Policy Cleanup".

Context:
- v1.34 Workshop Provider Checker Parity is complete and archived.
- TypeScript, Python, Rust, and Zig are supported counted Strategy languages through provider-gated runtime evidence.
- TypeScript/Python source-language artifact provenance remains provenance evidence, not WASM isolation.
- Rust/Zig remain immutable WASM/WASI Preview 1 artifact-backed lanes.
- TinyGo remains spike-only/hidden from production surfaces.
- Strategy execution must remain outside web/API/Go and behind runtime-service / Runtime Broker / provider boundaries.
- Several standing limitations are now worth polishing together:
  - Go TypeScript account-save/provider-proof drift.
  - Old production auth/account ownership deferred edges, especially local Workshop trust shortcuts.
  - No broader production sandbox certification yet.
  - Package ecosystems and dependency policy are intentionally unsolved.

Milestone intent:
Close or explicitly reframe the remaining runtime/account/security-policy edges so Coward's Game has honest, testable, production-facing boundaries for account-owned Strategy Revisions, provider proof, sandbox-readiness evidence, and package/dependency policy without changing runtime ownership or making unsupported sandbox claims.

Desired scope:
1. Inventory all current account save, account-owned revision, owner-debug, Workshop compatibility alias, competition entry, Go-owned read/write, provider-proof, sandbox-claim, and package/dependency surfaces affected by these limitations.
2. Clean up Go TypeScript account-save/provider-proof behavior so TypeScript account-save and any Go-owned account/entry surfaces either require current provider-grade proof where eligibility needs it or are explicitly scoped as non-execution draft storage with no misleading readiness claim.
3. Resolve old production auth/account ownership deferred edges:
   - Replace or tightly quarantine `player:workshop-local` and no-auth local trust shortcuts where they can affect persisted owner-debug/account-owned behavior.
   - Ensure owner-debug/private replay evidence is server-authorized and absent from public/default output.
   - Decide whether old Workshop compatibility API aliases should be removed, hidden, migrated, or documented as deprecated with tests.
4. Build a broader sandbox-readiness/certification contract:
   - Distinguish current runtime containment, hostile-code evidence, candidate lanes, unavailable lanes, and actual production sandbox certification.
   - Add fail-loud proof gates and public/developer labels so no current lane silently claims more isolation than it proves.
   - Do not certify a production sandbox unless the milestone produces the explicit evidence required.
5. Define and enforce package/dependency ecosystem policy for TypeScript, Python, Rust, Zig, and TinyGo:
   - Keep current no-rich-package/no-host-import boundaries intact unless a narrow, explicitly approved package lane is proven.
   - Document supply-chain, reproducibility, native-code, deterministic-build, privacy, and runtime-boundary requirements for future package support.
   - Add diagnostics and tests that prevent hidden package-path, host-path, token, env, DB, source, artifact, or private runtime leakage.
6. Preserve hard boundaries:
   - no Strategy execution in web/API/Go
   - runtime-service / Runtime Broker / provider boundary remains the hostile-code boundary
   - TypeScript/Python artifact provenance remains provenance evidence, not WASM isolation
   - Rust/Zig remain immutable WASM/WASI Preview 1 artifact-backed unless a future ABI milestone explicitly changes that
   - TinyGo remains spike-only/hidden from production surfaces
   - no public raw diagnostics, Strategy source, artifact bytes, host paths, env values, package paths, tokens, DB details, private runtime internals, StrategyMemory, SoldierMemory, or objective payloads
7. Add focused tests, privacy scans, boundary monitors, and at least one service-backed proof covering the corrected account/provider-proof path plus the sandbox/package-policy gates.

- after I approve, plan and execute autonomously as far as possible
- use subagents where useful
- validate/audit/verify before wrapping

## v1.36 Prompt

We're starting Coward's Game v1.36.

Please create a new GSD milestone with no workstream: "Competition Maturity".

Context:
- v1.35 should have cleaned up runtime/account ownership/provider-proof/sandbox/package-policy edges or explicitly documented what remains deferred.
- Coward's Game currently has exhibitions, resettable trial ladder seasons, counted Strategy eligibility, public standings/results/replay evidence, governance/status controls, and privacy-safe public player/Strategy pages.
- Competition has intentionally remained alpha-ish in places: resettable seasons, no durable rating promise, limited abuse/dispute/account-recovery maturity, and several public trust surfaces that need a more production-shaped policy.
- Strategy execution must remain behind runtime-service / Runtime Broker / provider boundaries, and public replay/result output must stay source/memory/objective/private-runtime safe.

Milestone intent:
Move the competition experience from alpha/trial posture toward a mature public beta by tightening season policy, entry eligibility, ranking/governance expectations, abuse/dispute handling, account-recovery assumptions, public trust copy, standings integrity, and replay/result realism without changing deterministic game rules or runtime ownership.

Desired scope:
1. Inventory current competition surfaces:
   - exhibition MatchSets
   - trial ladder seasons
   - counted/non-counted/degraded result policy
   - standings recomputation
   - entry eligibility and one-active-revision rules
   - same-user/multi-revision/self-play behavior
   - public result/replay/player/Strategy pages
   - governance/admin status marking
   - abuse/dispute/account recovery assumptions
2. Decide the v1.36 competition posture:
   - what remains "trial" or resettable
   - what can be called public beta
   - whether durable ratings remain out of scope
   - what public copy must say honestly about resets, counted status, degraded Matches, and dispute outcomes
3. Tighten entry and season rules:
   - ensure counted eligibility uses current provider-proof/language/runtime evidence
   - prevent stale artifacts, unsupported providers, hidden TinyGo, invalid provenance, or unavailable runtime lanes from entering counted competition
   - clarify same-user/multi-revision/self-play behavior for exhibitions versus ranked/trial competition
4. Mature standings and result governance:
   - make counted/non-counted/degraded/disputed/invalidated states recomputable and public-safe
   - ensure governance actions are auditable without exposing private runtime/operator internals
   - add clear player-facing explanations for why a Match/MatchSet did or did not count
5. Add abuse, dispute, and recovery policy surface appropriate for public beta:
   - define what is product behavior now versus future moderation/account-recovery work
   - add minimal UI/API/docs where needed for honest expectations
   - preserve privacy and avoid exposing Strategy source, private memory, objectives, raw diagnostics, tokens, DB details, or operator-only payloads
6. Improve public trust UX:
   - standings pages, competition pages, result pages, replay pages, and player/Strategy pages should make eligibility, counted status, season state, and evidence availability understandable without sounding scary or internal.
   - replay/result realism checks should remain part of verification, including visible Soldier/STONE positions inside board bounds and plausible canonical starts.
7. Add focused unit/integration/browser/service-backed E2E proof:
   - entry -> counted MatchSet -> execution -> result -> standings -> replay
   - degraded/non-counted/disputed/invalidated scenarios
   - privacy scans and boundary monitors
   - public copy validation for resettable/trial/beta posture

Hard boundaries:
- no game-rule changes unless explicitly justified and approved
- no Strategy execution in web/API/Go
- no new runtime/sandbox/package claims beyond v1.35 evidence
- no public raw diagnostics, Strategy source, artifact bytes, host paths, env values, package paths, tokens, DB details, private runtime internals, StrategyMemory, SoldierMemory, or objective payloads
- no durable permanent rating promise unless the milestone explicitly plans and proves it

Please run the normal GSD flow:
- create the milestone
- discuss phases sequentially
- after I approve, plan and execute autonomously as far as possible
- use subagents where useful
- validate/audit/verify before wrapping
