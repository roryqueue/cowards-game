## Narrative Findings (AI reviewer)

### Critical Issues

#### CR-01: The reviewed closure still incorporates absolute checkout paths

**Classification:** BLOCKER

**File:** `scripts/lib/v1-38-bounded-retry-v3-path-stable-custody-v1.ts:190-205`

**Issue:** `reviewedBody.installedClosureRoot` is copied directly from `authenticateV138RetryV3ExecutionClosure`. That historical helper's installed manifest records each resolved dependency edge with the absolute `dependencyRoot` (`r\0...\0${dependencyRoot}`), and can also retain absolute symlink targets. Consequently `reviewedClosureRoot` still depends on checkout/install location even though this helper labels it path-stable. The linked-worktree test hides the defect by symlinking every worktree `node_modules` back to the canonical checkout, so both executions resolve the same absolute package roots. A linked worktree with its own equivalent install, or a relocated checkout, produces a different reviewed root despite identical installed bytes. This directly violates the requirement that no absolute checkout path enter the reviewed root.

**Fix:** Build a new path-stable installed manifest rather than reusing `native.installedClosureRoot`. Label package contents and dependency edges with stable package identities and package-relative paths, hash the resolved bytes/modes, reject or normalize absolute symlink targets, and prove that two physically separate equivalent installs produce the same reviewed root. Keep the historical absolute-path installed root only in the explicitly local custody body if it is still needed there.

#### CR-02: A Plan-114 trio created in the required linked worktree can never pass canonical readiness

**Classification:** BLOCKER

**File:** `scripts/run-v1-38-bounded-retry-envelope-v3-live-v10.ts:314-318`

**Issue:** The prospective Plan-114 payload and supplement bind `input.reviewedClosure.localExecutionClosureRoot`. Plan 114 is required to derive and commit its candidate evidence in a linked worktree, and the Plan 113 test explicitly proves that the linked worktree's local execution root differs from the canonical root. Later, `authenticateFutureCustody` derives the closure again from the current canonical checkout (lines 460-466) and demands byte-for-byte equality with that linked-produced payload. The canonical local root therefore changes the payload, review, carrier, and supplement roots, so `--check-reviewed-live-ready` and production fail even for a truthful Plan-114 publication. Conversely, publishing the canonical local root would make the required linked-worktree actual modes fail. The future chain is internally unsatisfiable.

**Fix:** Give portable reviewed custody and canonical local execution custody separate contract fields and verification paths. Plan 114's linked-worktree observations should bind the path-stable reviewed root while explicitly recording the linked local root only as local review context. Independently derive and pin the canonical production local root under a clearly local name, then require that canonical value before and after the producer call. Add an end-to-end test that creates the Plan-114 trio and supplement in a linked worktree, installs them in a disposable canonical-equivalent checkout, and successfully executes readiness without invoking production.

#### CR-03: The effectful producer receives pair bytes re-read after authentication with validation disabled

**Classification:** BLOCKER

**File:** `scripts/run-v1-38-bounded-retry-envelope-v3-live-v10.ts:524-534`

**Issue:** `authenticateFutureCustody` authenticates the sealed pair, but its result does not carry that pair forward. The live function then performs fresh, following `readFileSync` reads of the seal and envelope and passes those unchecked objects through `checkPair` while setting `validateInputs:false`. A replacement or race between admission and these reads can therefore supply a forged envelope to the sole effect owner after all gates passed. The `as any` cast removes the last type-level boundary check. Frozen live-v9 avoided this by passing the already authenticated `ready.pair.seal` and `ready.pair.envelope` to the producer.

**Fix:** Have the pair authenticator return the exact validated, canonical seal/envelope objects and propagate them through `authenticateFutureCustody`; pass only those frozen values to `runV138V3ProductionLive`. Do not re-read the working tree after admission. Retain no-follow/current-mode checks while authenticating the pair and remove the `as any` cast by returning the producer's exact pair type.

#### CR-04: Post-run success omits the required reproduction-v17 custody check

**Classification:** BLOCKER

**File:** `scripts/run-v1-38-bounded-retry-envelope-v3-live-v10.ts:509-521`

**Issue:** `assertPostRun` checks output presence and calls the generic producer outcome checker, then stops. The aliased `checkV138LiveV10ReproductionV17ForReview` is never called on the actual artifact/journal. The generic outcome checker validates only a small success subset (receipt-root linkage, status, accepted count, and cleanup); it does not enforce the reproduction-v17 exact schema, receipt-root derivation, 540 charged count, admitted calibration root, runtime/sampling fields, exhaustive privacy projection, exhaustive false-authority fields, journal ownership/route joins, or the final no-change recheck. Frozen live-v9 performs all of those additional checks on bounded success. A malformed or authority-bearing reproduction-v17 artifact can therefore pass live-v10 post-custody.

**Fix:** Restore the frozen live-v9 success path: read the canonical reproduction artifact and journal with no-follow, size, mode, and change checks; call `checkV138LiveV9ReproductionV17ForReview` (or the live-v10 alias) with the actual artifact, records, and outcome; then recompute the published outcome and require it to remain identical. Add actual post-run mutations for every schema/privacy/authority/journal join.

#### CR-05: Immutable and protected history are asserted by literals, not authenticated

**Classification:** BLOCKER

**File:** `scripts/run-v1-38-bounded-retry-envelope-v3-live-v10.ts:153-213`

**Issue:** `assertExactAddPublication` proves the original add commit and that current bytes equal the original, but never checks `git log <commit>..HEAD -- <paths>`. A later edit/delete followed by restoration is accepted despite the immutable-history/no-rewrite contract. `assertPairAndStop` likewise checks only the pair's stored `protectedHistoryRoot` literal and a Plan-93 byte hash; it does not independently enumerate the protected branches, recompute the expanded protected-history manifest, prove those paths were not rewritten after the pair commit, or enforce Plan-93 no-rewrite and required semantics. Because live-v10 also invokes the producer with `validateInputs:false`, no downstream call repairs this missing authentication.

**Fix:** Add successor-rewrite checks for the corrected publication, both Plan-112 publications, pair, and Plan-93 paths. Reproduce live-v9's independent protected-branch enumeration and expanded-manifest derivation, and compare it to the exact protected-history evidence before readiness or production. Validate Plan-93's required stop semantics as well as its bytes. Mutation tests must include edit-and-restore histories and direct protected-branch tampering.

### Warnings

#### WR-01: The exported prospective renderer accepts fabricated closure evidence

**Classification:** WARNING

**File:** `scripts/run-v1-38-bounded-retry-envelope-v3-live-v10.ts:301-313`

**Issue:** `deriveV138LiveV10ProspectiveContractsForReview` validates only the reviewed commit/root string formats, exact path list, and the false pathname claim. It does not recompute either root or compare the supplied custody object to a derived closure. It will therefore render a zero-findings payload, review, carrier, and supplement from arbitrary 64-hex roots. The test deliberately relies on this by fabricating the source commit and both roots. Production currently re-derives the closure later, so this is not by itself an execution bypass, but the exported `ForReview` API is unsafe evidence tooling and can generate convincing false Plan-114 materials.

**Fix:** Require a repo root and independently derive/validate the closure inside the renderer, or accept an independently derived expected closure and call `checkV138PathStableCustodyForReview` before rendering. If the function is only a pure byte renderer, make it non-exported and rename it so it cannot be mistaken for an evidence validator.

#### WR-02: The custody mutation test does not mutate any custody input

**Classification:** WARNING

**File:** `scripts/run-v1-38-bounded-retry-envelope-v3-live-v10.test.ts:117-132`

**Issue:** The test labels cases as relative-path, mode, blob, bytes, recursive-import, installed-input, native-source, Git-executable, and hardened-argument mutations, but only edits fields on an already derived result and asks an equality checker to reject the changed object. The mode/blob/bytes cases are identical except for an arbitrary replacement of `checkoutManifestRoot`; no file mode, Git blob, working byte, import, installation, executable, or argument is changed. This gives false confidence in the derivation boundary and is why the absolute installed-path defect is not detected.

**Fix:** Perform each mutation against an isolated repository/install fixture, re-run `deriveV138PathStableCustody`, and assert the appropriate derivation failure or root change. Include a physically separate but byte-identical install as the positive path-stability control, plus an absolute package-root relocation test.
