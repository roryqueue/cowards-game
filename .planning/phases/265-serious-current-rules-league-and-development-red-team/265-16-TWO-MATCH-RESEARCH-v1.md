2. **Allocation gate:** Fresh exact-key schema binds `matchCount: 2`, both distinct slot/request/pair roots, seat schedule, current engine tuple, isolated runtime image/limits, source HEAD, approval window/cost snapshot, and finite retained-byte references. Commit as a direct child of the fixed source HEAD before entry. New private store and allocation must not alias any old root/path.
3. **Entry/capacity gate:** Unique ROOT entry authenticates committed allocation bytes and lineage; create exact private store; take fresh same-process RAM/disk/time observations and enforce full two-Match reserves before any debit or provider creation. Re-observe before each Match. Existing capacity functions accepting only v2 zero-Match allocations cannot be treated as supporting this new mode without a source-reviewed explicit extension.
4. **Execution gate:** For each ordinal, write/verify the immutable pair and debit before creating either seat provider. Issue only through existing host supervision, canonical `MATCH_KERNEL`, exact fixed V8 sandbox runtime and source closure. Preserve existing 1,000/2,500/5,000/600,000 ms bounds. Match 1 starts only if Match 0 terminal, cleanup, ledger and capacity state are all known-good; otherwise close with one Match attempted and the second unused. No retry or replacement.
5. **Closeout gate:** Emit redacted compact per-Match result (status/reason enum, duration/counters, cleanup and replay/chronicle integrity roots) with no strategy source, memory, objectives, raw payloads, errors or stdio. One independent retained verifier authenticates both planned slots, attempted debits, omitted second slot if stopped, source/HEAD, canonical replay/Chronicle integrity, store inventory/permissions, resource receipts and terminal cleanup. Failures remain failures; empty/unknown evidence is not success.
