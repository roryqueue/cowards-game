### Control-repair decision

The source defect is specifically observability/order: synchronous `Atomics.wait` blocks the broker event loop that would deliver parent-side worker `error`/`exit` callbacks. A future async wait could let callbacks and the atomic ready notification race within the same absolute deadline, then re-read the atomic predicate before classifying, terminating on failure/timeout. This is a credible source-level control improvement, but feasibility remains MEDIUM until the actual supported Node version and the proposed async primitive/event protocol are verified in focused tests; do not assume `Atomics.waitAsync` availability. A bounded alternative using a trusted message channel must likewise prove the readiness message cannot be forged by guest code and atomics remain authoritative. If neither can preserve the deadline and no-guest-authority invariant, implement attribution only and state that no control repair is justified.

The harness data URL may be precomputed once per broker source instead of calling `workerUrl(encodeURIComponent(harness))` in each `construct()`. This preserves fresh workers and is a small bounded optimization candidate. Keep precomputation within existing outer wall accounting (no timer reset, excluded host work, or widened allocation); compare source-only/inert behavior and retain exact URL/harness roots. This is not a proven fix, and must not be represented as resolving v15-4.
